# Codex interim strategy review — read after first implementation pass

> Correction (2026-09-30): ownership is now Claude implements, Codex reviews the logic (this document's own review role is unaffected). Separately, the "wrong sector" exclusion referenced in item 6/resolution below no longer exists: candidates and their sector labels are user-chosen (any sector), not restricted to automotive. `maxSectorWeight` concentration caps apply independently per user-declared sector. See STRATEGY.md for current behavior.

Do not treat this as unrelated robustness work: these directly change profitability/time integrity.

1. Position sizing: StrategyConfig currently permits maxHoldings=5,maxWeightPerHolding=1. `screen` selects all with weight=1 and clamps only reported cash. Enforce sum(weights)<=1 (e.g. cap equal weight to min(maxWeightPerHolding,1/maxHoldings), or reject incompatible config). Add a test proving negative cash/leverage is impossible.
2. Check all actual source timestamps, not only envelope knownAt. Current/prior consensus source.knownAt, catalyst source.knownAt, optional diagnostic source/knownAt must be <= relevant publication/decision. Otherwise envelope backdating bypasses point-in-time discipline.
3. Quarter bridge inputs (netInterest/tax/noncontrolling/preferredClaims/shares) currently have no provenance or assumption labels. Add explicit known-at provenance/assumption metadata for the bridge and segment forecast values; their numeric plausibility alone is insufficient. Expose user-supplied full-company coverage as unverified in output.
4. Forecast horizon: four arbitrary consecutive FUTURE quarters can be years in the future yet called NTM. Define and enforce the first admissible quarter in KST. Suggested convention: first quarter is the calendar quarter immediately after the KST decision quarter; exactly four consecutive quarters. Label this next-four-full-fiscal-quarter EPS (not exact rolling 12-month EPS). If choosing current not-yet-ended quarter instead, document and enforce consistently. No far-future horizon allowed even with matching consensus.
5. Same-ticker snapshot revisions: screen must select the latest available forecast at decision time (or reject ambiguous duplicates); do not allow double allocations to one ticker or cherry-pick the biggest gap. Service should include snapshot IDs/hash in selected/evaluations for traceability.
6. Need declared company name/exchange/type or equivalent attested metadata and common-stock check, so suffix-only ticker not silently treated as verified KOSPI membership. Clearly label user-declared universe membership.
7. Avoid future simulation advertised as observed outcome: replay accepts outcome prices, so require completed session close <= evaluation clock in API/CLI for non-synthetic replay, or explicitly label future-projected paths as synthetic. Recorded decision/config must not be retrospectively called forward strategy performance just because candidate was recorded earlier.
8. Keep README honest about single-cohort replay, manually supplied data, synthetic example, and no independently verified profitability.

Independent numerical oracle is in docs/STRATEGY_LOGIC_REVIEW.md.
9. realizedEps errorPct currently divides by realized sum even if zero/negative. Use signed absolute errorKRW and percentage relative to abs(realized) only when denominator > threshold, else null+reason. Validate duplicate ticker-quarter actuals, actual basis/scope/unit, and knownAt<=evaluation clock; otherwise omit optional forecast accuracy for v1 rather than output Infinity or an inverted accuracy interpretation.
10. Replay contract should include full config, snapshot IDs/hashes, calendar/price provenance and evidence label even for incomplete/no_trade. Optional evidenceModes per eligible ticker alone loses labels when all candidates are ineligible. Add explicit portfolio weight/cash, turnover and normalized-fractional-total-return simulation note.
11. Comparisons of instants must use epoch in replay too: `input.decisionAt !== selection.decisionAt` incorrectly rejects equivalent offset representations.
12. Forward evidence bypass in service.ts: inline candidates can declare evidenceMode:'forward' without any server record; only forecast.recordEvidenceMode is checked, so forward forecast + historical/synthetic consensus/catalyst is labeled forward. Require ALL signal input references to be forward records available by decision for forward label; inline inputs must be synthetic or historical-unverified. Aggregate weakest evidence mode across ALL records, with synthetic dominating, not just forecast. Persist/validate synthetic on the journal record and don't let forward+synthetic become forward.
13. ScreenRequest.decisionAt uses z.string() rather than validated datetime. Invalid date causes NaN comparisons to fail open, bypassing recordedAt/knownAt guards. Use isoDateTime schema and validate service public methods, not only HTTP call sites.
14. Actual forward EXPERIMENT performance requires the decision/selection/config to be recorded at decision time (before entry). Candidate forecasts recorded earlier are insufficient: selecting old IDs and favorable rules today is retrospective research. Either persist immutable screen decisions server-timestamped and have replay consume their IDs, or explicitly label every recomputed past decision replay retrospective/unverified even with forward input records. Do not accept client-forged ScreenResult as authoritative in authenticated API/CLI replay.

## Reproduction on first-pass code (Codex, during implementation)
Pure screen with two identical ticker 123450 candidates, decision 2026-01-15, forecast horizon 2027Q1–Q4, envelope consensus knownAt 2026-01-05 but source.knownAt 2030-01-01, maxWeightPerHolding=1 and maxHoldings=5 returned two selected entries, totalWeight=2, eligible=true. This simultaneously reproduces duplicate allocation, leverage, future-source leakage, and far-horizon misuse. Test each independently after fixing, not only this combined case.

## Resolution (2026-09-30, Codex direct implementation authorized by user)
1–6: duplicate candidates rejected; sector/position/capacity limits enforced; all source/assumption times checked; KST next-four-full-quarter horizon fixed; company/scope declaration and common-stock filter added. Inputs, IDs/hashes and user-attested coverage retained.
7–8: non-synthetic replay enforces completed outcomes known at evaluation; every recomputed run is explicitly retrospective research; CLI/API and remaining data limitations documented in STRATEGY.md.
9: actual EPS requires consistent scope/basis/unit, unique periods and publication after period end; zero/near-zero denominator yields null percentage plus absolute error.
10–11: full config, source/input hashes, metadata on incomplete/no-trade too; turnover and cash-weighted benchmark added; epoch comparison used.
12–14: all four input records determine evidence mode; inline forward forbidden; invalid dates rejected; server-clock checks applied to forward records. v1 intentionally labels recomputed decisions retrospective, instead of claiming a pre-registered experiment.
The risk addendum is implemented in risk.ts and screen.ts. See implementation report and independent risk/integrity tests. These fixes establish calculation integrity, not profitability or independently verified data provenance.
